## Domain 1: Vector Math & Semantic Embeddings

### 1. What is an Embedding under the hood?
* A vector embedding is a sequence of floating-point numbers (e.g. 384 dimensions in `bge-small-en-v1.5`) generated by the final hidden state (or mean-pooled token states) of a Transformer encoder.
* In mathematical terms, an embedding maps a variable-length string of text $T$ into a fixed-dimensional coordinate in a continuous semantic vector space:
  $$f: \text{Text} \longrightarrow \mathbb{R}^{384}$$
* **Why 384 dimensions?** Larger models (like OpenAI `text-embedding-3-large` with 3,072 dimensions) capture slightly more fine-grained nuances, but require **8x more RAM and 8x more memory-bus bandwidth**. For customer reviews, 384-d gives 95%+ of the retrieval quality while running entirely in CPU cache with sub-millisecond distance computations.

### 2. Cosine Distance vs. Euclidean (L2) vs. Dot Product
* **Dot Product:** $\mathbf{u} \cdot \mathbf{v} = \sum_{i=1}^{d} u_i v_i$
* **Cosine Similarity:** $\cos(\theta) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\|_2 \|\mathbf{v}\|_2}$
* **Cosine Distance:** $D_{\text{cos}}(\mathbf{u}, \mathbf{v}) = 1 - \cos(\theta)$
* **The Production Optimization Trick:** If we **L2-normalize** every vector at ingestion time so that $\|\mathbf{u}\|_2 = 1.0$, then:
  $$\cos(\theta) = \mathbf{u} \cdot \mathbf{v}$$
  The expensive square roots and divisions disappear completely! Calculating cosine similarity becomes a single, lightning-fast dot product.

## Domain 2: Vector Indexing & Hardware Mechanics (HNSW vs. SIMD)

### 1. What is HNSW (Hierarchical Navigable Small World)?
* **The Problem:** If you have 100,000 vectors and want to find the top 5 nearest neighbors, comparing your query to all 100,000 vectors (brute-force scan) takes $O(N \cdot d)$ operations.
* **The Solution:** HNSW organizes vectors into a multi-layer graph (similar to a Skip List). The top layers have few long-distance highway connections for rapid coarse navigation; the bottom layer contains all vectors with fine-grained local connections.
* **Key Hyperparameters:**
  * $M$ (e.g. 16): Maximum number of bi-directional connection links per node. Higher $M$ = better recall, but uses more memory.
  * $ef_{\text{construction}}$ (e.g. 128): Size of the dynamic candidate list during graph construction. Higher = slower indexing, but higher graph quality.
  * $ef_{\text{search}}$ (e.g. 64): Size of the candidate list evaluated during a search query.

### 2. The "HNSW Isolated Island" Bug (Why Plan A is Essential)
* In standard HNSW, if you run a query with a strict pre-filter (e.g. *"Only search orders from customer X"* where only 10 rows match out of 100,000), the graph traversal enters nodes that are not allowed by the filter.
* The search algorithm gets stuck because all valid nodes are separated by vast "oceans" of invalid nodes, causing retrieval recall to drop from 95% down to 30%!
* **DualQuery's Defense (Plan A):** When the filter matches $\le 1,500$ rows, we completely turn off HNSW. We run an exact hardware-accelerated **SIMD scan** directly on the candidate subset.

### 3. What is SIMD (Single Instruction, Multiple Data)?
* Modern CPU cores have 256-bit or 512-bit vector registers (Intel/AMD AVX2, AVX-512, Apple NEON).
* A single floating-point number is 32 bits (4 bytes).
* In a 256-bit register, the CPU loads **8 floats simultaneously** and computes their product in **one single CPU clock tick**.
* This is why scanning 1,500 384-dimensional vectors on CPU takes $<4$ milliseconds without needing an expensive GPU.

## Domain 3: Lexical IR & Hybrid Fusion (BM25 + RRF)

### 1. Why Dense Vectors Fail on Exact Terms
* Dense embeddings understand concepts, but are terrible at exact serial numbers, error codes, and unique brand names.
* If a customer writes: *"Error code ERR_9021 on invoice #8841"*, an embedding model might map it to "software glitch" or "invoice issue" rather than matching the exact identifier.

### 2. How BM25 Works (Best Matching 25)
* BM25 improves on TF-IDF by adding two crucial non-linear dampening factors:
  1. **Term Frequency Saturation:** Hearing a word 10 times doesn't mean the document is 10x more relevant than a document with 2 mentions. BM25 curves off term frequency.
  2. **Document Length Normalization:** A short review that mentions "battery" twice is much more focused on battery issues than a 50-page manual mentioning "battery" twice.

### 3. Reciprocal Rank Fusion (RRF)
* How do you combine a cosine score (which ranges from -1 to 1) with a BM25 score (which is an unbounded positive number)? You cannot simply add them!
* **The Solution:** RRF ignores the raw score values and operates strictly on **rank positions**:
  $$\text{RRF\_Score}(d) = \frac{1}{k + \text{rank}_{\text{dense}}(d)} + \frac{1}{k + \text{rank}_{\text{bm25}}(d)}$$
  (where standard constant $k = 60$).

## Domain 4: Database Internals & Query Planning (DuckDB OLAP)

### 1. Why Columnar Storage (OLAP) Beats Row Storage (OLTP) for Analytics
* **PostgreSQL / MySQL (Row-oriented):** Data is stored row-by-row on disk (`[ID, Name, Date, Amount], [ID, Name, Date, Amount]`). If you run `SUM(amount)`, the CPU must read the customer name, address, and date into memory just to throw them away.
* **DuckDB (Columnar):** All `amount` values are stored sequentially in a contiguous array on disk and in RAM. Calculating `SUM(amount)` over 100,000 numbers is a single contiguous memory read, enabling vectorized execution at memory bandwidth speeds (>10 GB/s).

### 2. Pre-Flight Cardinality Probing
* Query planners in enterprise databases use table statistics (histograms) to estimate how many rows will match a query.
* Instead of guessing, `DualQuery` runs a lightweight `<2ms` pre-flight query:
  ```sql
  SELECT COUNT(DISTINCT order_id) FROM orders WHERE order_status = 'delivered' AND payment_value > 300;
  ```
* Based on this exact number ($\hat{N}_{\text{cand}}$), the optimizer chooses Plan A (SIMD) or Plan B (HNSW).

## Domain 5: Compilers, AST & Security (SQLGlot & PII)

### 1. What is an Abstract Syntax Tree (AST)?
* When code or SQL is parsed, the raw text string is transformed into a hierarchical tree data structure:
  ```
            Select
           /      \
      Columns     Where
      [price]    /     \
                GT      price, 300
  ```
* Text regex checks (like `if "DROP" in sql:`) are dangerously easy to bypass (e.g. `/* comment */ DROP`, hex encoding, or table aliases).
* An AST parser like `SQLGlot` breaks the query into formal grammar tokens, making security validation 100% deterministic.

### 2. The 5 Security Gates
1. **Gate 1:** Root AST node must strictly be `exp.Select`. Any `exp.Drop`, `exp.Delete`, `exp.Update` is immediately rejected.
2. **Gate 2:** File-system / network functions (`read_csv`, `httpfs`) are blocked.
3. **Gate 3:** Referenced tables are checked against a strict role whitelist.
4. **Gate 4:** PII columns (customer phone, CPF tax ID, street address) cannot be selected in the outer query.
5. **Gate 5:** Mandatory Row-Level Security (RLS) predicates and `LIMIT 1000` are injected directly into the AST before execution.

## Domain 6: Modern Agentic Protocols & Evals (MCP & RAGAS)

### 1. What is Model Context Protocol (MCP)?
* Created by Anthropic (November 2024), MCP is an open JSON-RPC 2.0 protocol that standardizes how AI agents (Claude Desktop, Cursor, local agent runtimes) discover and execute tools on external systems.
* Instead of writing custom API wrappers for every model, an MCP server declares its tools (`get_governed_catalog`, `execute_hybrid_query`) and any MCP client can consume it automatically.

### 2. Why "Plan-Shipping" Beats "Data-Streaming"
* Standard database MCP servers run `SELECT * FROM orders` and serialize 5,000 rows into JSON text to send back to Claude Desktop.
* **DualQuery's Zero-Trust Moat:** We send the *plan* to the database, compute the mathematical aggregation *locally*, and only ship back the 3-line summary and 5 redacted citation snippets.
